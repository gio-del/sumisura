# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sumisura — a self-hosted tool that generates a tailored, one-page CV (PDF) and cover letter for a specific job application, and tracks the Job Listings/Applications built around it. It is not a generic resume builder: it is single-tenant, built around one person's career history (the installation owner's), and produces a *Tailored CV* per *Job Description* via a Claude Code skill, not a build script. A standalone local web app sits alongside the skill for browsing/editing Master Data and tracking Job Listings and Applications.

Positioning note (ADR-0036): the project is self-hostable by other people — the `data/` stubs, the README quickstart and the docs exist for them — while staying single-tenant, localhost-first and free of accounts. "CV" remains the domain term throughout code, `CONTEXT.md` and ADRs; "resume" is used only in marketing surfaces (repo description, topics, landing page).

Read `CONTEXT.md` first for the domain vocabulary (Master Data, Entry, Client Engagement, Selection, Rewrite, Tailored CV, Job Listing, Application, etc.) — the rest of this file assumes it. Check `docs/adr/` for why the architecture looks like this before proposing to change it.

## Running it

The tailoring "build" is the `tailor-cv` skill (`plugins/sumisura/skills/tailor-cv/SKILL.md`, invoked as `/sumisura:tailor-cv`) — invoke it with a job description (pasted text or URL), a reference to an already-tracked Application, or nothing (Default Mode). It walks: Selection → Rewrite (plus a Cover Letter draft from `data/cover-letter-snippets/`, or fresh prose, whenever a Job Description is given — not in Default Mode) → Text Review (approval required, CV and Cover Letter approved independently) → Render → Visual Review (approval required), recording the Generation against the tracked Application afterward when that's the input mode used. Along the way it runs the web app's automated quality checks (groundedness before Text Review; page count, ATS-parsability and `lang` before Visual Review) by shelling out to `backend/cmd/cvcheck` through `plugins/sumisura/skills/tailor-cv/scripts/quality-check.sh` — the same Go check code the app calls, offline, no running backend needed (ADR-0028). Checks are advisory and never block a checkpoint.

Rendering requires the `typst` CLI on `PATH`. To render manually once a tailored data file exists:
```
typst compile --root . template/cv.typ output/<slug>/cv.pdf --input data=output/<slug>/data.json
typst compile --root . template/cover-letter.typ output/<slug>/cover-letter.pdf --input data=output/<slug>/cover-letter-data.json
```

The web app (backend + frontend) runs via `docker-compose up` — backend on `127.0.0.1:8080`, frontend on `127.0.0.1:5173`, both localhost-only with no auth. Generation calls the Claude API directly (ADR-0005; copy `.env.example` to `.env` and set `ANTHROPIC_API_KEY` — `docker-compose.yml` forwards it into the backend container). Each kind of Claude call (call site) runs on its own default model — Haiku 4.5 for the RAL/Contact extraction calls and Application Method inference, Sonnet 5 for everything else — overridable per call site with `SUMISURA_MODEL_<CALL_SITE>` or for all of them with `SUMISURA_MODEL_DEFAULT` (ADR-0025; the table lives in `backend/internal/claude/models.go` and README's "Claude models per call site"; any model a call site can default to must also be priced in `backend/internal/claude/pricing.go`). Render shells out to the same `typst` CLI the skill uses, so the backend needs `template/` and `output/` alongside `data/` under one `PROJECT_ROOT` (see ADR-0012). See `README.md` for the API surface and frontend dev commands.

Stopping the backend (`docker compose down`, Ctrl-C in a local `go run ./cmd/server`) is graceful: it stops accepting connections, drains in-flight requests for up to 15s, then cancels whatever is still running so its outbound Claude calls stop. The server's connection limits are explicit but deliberately include no total-response cap — a Generation legitimately runs for minutes; the Claude-calling routes carry a 10-minute request deadline instead. See `docs/adr/0021-no-total-response-timeout-bounded-drain-instead.md` before changing any of those values.

An opt-in LAN-reachable mode (issue #57) exists for reaching the app from other devices on the same network: set `BIND_ADDR=0.0.0.0` and `LAN_AUTH_TOKEN` in `.env` and run `docker compose --profile lan up`. This is an explicit, opt-in exception to ADR-0004's "localhost-only, no auth" default, not a reversal of it — the default `docker-compose up` invocation is unchanged. See `README.md`'s "Optional: LAN-reachable mode" section for the tradeoffs (shared static secret via `X-Sumisura-Token`, no TLS, single trusted network assumed). A browser exchanges the token once via `POST /api/auth/session` for an HttpOnly access cookie (an HMAC keyed by the token, so rotating it signs every device out) that the gate accepts in place of the header — needed because PDF links, the PDF iframe and Company Logo images can't carry a custom header (issue #181). `GET /api/auth/status` and `/api/auth/session` are the only ungated `/api` routes.

Job Listing and Application records carry a `schemaVersion` (ADR-0034, `backend/internal/tracking/schema.go`). Records written before it existed read as legacy, and `backend/cmd/migrate-records` migrates them: `cd backend && go run ./cmd/migrate-records -data-dir ../data` is a dry run that only reports (exit 3 when anything is pending); add `-write` to apply. It backfills only `freshnessStatus` on Job Listings and, for Applications still at Saved, `statusUpdatedAt` plus a single Saved `statusHistory` entry from the Job Listing's `savedAt`; it never synthesises history past Saved, and never fills a legacy Generation's `sourceSnippetIds`/`entryIds`/`usage`/`language`. `data/jobs/` and `data/applications/` are gitignored, so never run it with `-write` against a real `data/` from a test or an experiment — use a temp copy. When adding a field to either record, bump `CurrentSchemaVersion` and teach `MigrateRecords` the step (see the comment in `schema.go`) instead of adding another "absent in older records" tolerance to a reader. See `README.md`'s "Migrating Job Listing and Application records".

The frontend's API types (`frontend/src/api/types.ts`) are hand-written and held to the backend by contract fixtures (ADR-0035): `backend/internal/api/contract_test.go` captures every JSON route's real response into `frontend/src/api/contract/fixtures/`, and `frontend/src/api/contract/contract.ts` type-asserts each one under `tsc -b`. The rule: a change to any response shape regenerates the fixtures with `cd backend && UPDATE_CONTRACT_FIXTURES=1 go test ./internal/api -run TestContract` and updates `types.ts` in the same change, until both `go test ./...` and `npm run build` pass. Never hand-edit a fixture, and never widen a type or add an exemption just to silence a failure — an exemption is only for a variant the scenario genuinely cannot reach, with the reason beside it. A new route needs a fixture in `contractFixtures` plus an assertion in `contract.ts`, or a reasoned entry in `contractExemptRoutes` if it has no JSON body. See `README.md`'s "API contract fixtures".

Note: ADR-0001 ("no Node.js/JS toolchain") only ever applied to the tailoring pipeline itself and has since been superseded by ADR-0004, which added the standalone web app (Go backend + React/TS/Vite frontend, see ADR-0009). The tailoring pipeline still has no Node/JS involvement — that part of ADR-0001's reasoning stands — but the repo as a whole now does.

## Architecture

- `data/profile.yaml` — contact info + Static Sections (education, publications, awards, activities, languages). Always included in full, never selected or rewritten. A missing `profile.yaml` is a setup step, not a fault — `masterdata.GetProfile` returns `ErrNoProfile` and the API answers 404.
- `data/experience/*.md`, `data/projects/*.md` — Master Data. One file per Entry: YAML frontmatter (`employer`/`client`/dates/`tags`/…) + Markdown bullets. A single employer can have multiple Entries (one per Client Engagement, e.g. `data/experience/example-client-*.md`) so Selection can surface one client's work independently of another's.
- `data/cover-letter-snippets/*.md` — optional Master Data. One file per Cover Letter Snippet: YAML frontmatter (`kind`, optional `tags`) + a Markdown paragraph body.
- **All of the above are gitignored** (ADR-0037, ADR-0038): they name the installation owner, their employer and their clients. The repo tracks stubs under `data/examples/` (`profile.yaml`, `experience/`, `projects/`, `cover-letter-snippets/`) and setup copies them across with `cp -r data/examples/. data/`. Never commit a file under `data/` other than the examples, and when adding a Master Data file type, ship its stub in `data/examples/` and gitignore the live path. A missing directory is an ordinary empty state, not an error — `masterdata.ListEntries`/`ListSnippets` already return nil for it.
- `template/cover-letter.typ` — the Cover Letter's equivalent: reads a seven-field JSON (contact fields + `body`) and lays it out, no drafting logic.
- `template/cv.typ` — pure presentation. Reads one assembled JSON file (path passed via `--input data=...`) and renders it; contains no relevance/selection logic. The Tech Stack section it renders is expected to already be derived (deduplicated `tags` of the selected Entries) by whoever assembled the JSON — the template just prints it.
- `output/` — gitignored. Rendered PDFs and the per-Generation assembled JSON are derived artifacts, not Master Data. Every Generation writes to its own `output/<label>-<UTC yyyymmdd-hhmmss>/` directory (`-2`, `-3`, … if taken) and never into an existing one (issue #105) — the rule lives in `generation.Render` for the app and is mirrored in prose by SKILL.md step 5. Records may outlive their files; a missing directory is expected, not an error. The skill also writes its Selection + Rewrite result into that directory as `selection.json`, so a groundedness verdict can be re-derived later.
- `.claude-plugin/marketplace.json` + `plugins/sumisura/` — a repo-local Claude Code plugin marketplace holding this repo's own skill(s), currently just `tailor-cv` (`plugins/sumisura/skills/tailor-cv/SKILL.md`), the skill that drives the whole tailoring pipeline described above. Kept separate from the author's general-purpose personal skills (`develop`, `tdd`, `domain-modeling`, …), which stay synced in via `skills-lock.json` from an external repo and are untouched by this one.
- `backend/` — Go HTTP API (see `backend/internal/api`) that reads/writes the same Master Data files under `data/` that the skill uses. `backend/cmd/server` is the API's entrypoint; `backend/cmd/cvcheck` is an offline CLI over the Generation quality checks (`generation.CheckSelectionGroundedness`, `generation.CheckRenderedCV`), which the skill shells out to. Every write under `data/` goes through `backend/internal/atomicfile`'s `WriteFile` (temp file in the same directory, then rename) so an interrupted write leaves the previous record intact; writes under `output/` stay on plain `os.WriteFile`, since derived artifacts can be regenerated (ADR-0018). Every API route that rewrites or deletes a record a user may be holding open also honours an optional `If-Match` version token (`backend/internal/recordversion`, issue #89): the store checks it right before that atomic write and the handler maps a mismatch to 409, while a request without the header writes unconditionally so the skill and extension are unaffected. A new record-writing route should do the same, and the frontend control behind it should send the token and show `ConflictAlert` on 409 — see README's "Lost-update protection" for the routes covered.
- `frontend/` — React + TypeScript + Vite app consuming that API.
- `Dockerfile` + `docker-compose.release.yml` — the published image and the compose file that runs it (ADR-0039): one container where the Go backend also serves the production frontend build (`STATIC_DIR`, SPA fallback for non-`/api` paths, `immutable` on hashed assets), on one port with no CORS. `docker-compose.yml` and `backend/Dockerfile` remain the *development* pair and are unchanged — Vite keeps hot reload there. LAN mode's token gates `/api/*` only; the frontend's own files load without it. CI builds this image and smoke-tests it (start, app shell, client route, 404 on an unrouted API path, a one-page render) on every change.

Adding a new job or project means adding a new Markdown file under `data/experience/` or `data/projects/` following the existing frontmatter shape — not writing code.

## Keeping docs in sync

Whenever a change alters something `README.md`, `CONTEXT.md`, `docs/adr/`, or the docs site (`site/src/content/docs/`) documents (a new/changed API route, a new top-level directory, a new running-it step, a superseded decision, anything a self-hoster configures or runs), update that documentation in the same session/commit as the code change — don't leave it for a later pass.

The split is by audience: `site/` holds what a **self-hoster** needs (quickstart, Master Data, tailoring, configuration, LAN mode, upgrading, troubleshooting); `CONTRIBUTING.md` holds what a **contributor** needs (dev loop, tests, contract fixtures); `README.md` is the pitch plus a quickstart that links out; `CONTEXT.md` and `docs/adr/` stay the source of truth for vocabulary and decisions, and the site links to them rather than copying them.
